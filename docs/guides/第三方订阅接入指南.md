# 第三方订阅接入指南

本文说明开放平台 API 应用如何订阅事件、接收签名推送、查看报文和恢复失败投递。业务应用模板通知是另一种接入，见[业务应用指南](第三方业务应用开发指南.md)。

## 1. 平台准备与权限

1. 在开放平台创建 API 应用，取得 **应用 ID、Client ID、Client Secret**，三者不要混用。
2. 配置应用允许调用的接口/API Group，确认应用创建人对目标设备等数据具有访问权限。
3. 使用具备应用查询、保存权限的管理身份配置订阅；该身份与接收端用于验签的 Client Secret 不是一回事。
4. 准备平台服务端可达的 HTTP 接收 URL，生产使用 HTTPS。

API 查询与订阅使用应用许可约束下的创建人当前数据身份，同时遵守租户及资产范围。OAuth2 不会绕过数据权限，超管创建也不等于移除租户约束。设备事件通常还要求设备 query 功能许可；有订阅管理权限不代表能订阅所有数据。

订阅和当前查询可能因时间不同出现差异，例如删除事件使用删除前归属，而设备删除后已无法查询；不能仅凭“事件有、当前查询无”判断越权。

## 2. 配置订阅

可以在应用的订阅配置页面完成，也可调用接口。以下路径相对于平台 API 根地址，保留实际网关前缀；使用具备对应管理权限的身份认证。

公共前缀：`/application/{applicationId}/subscriptions`。

| 操作 | 方法及后缀 |
| --- | --- |
| 获取事件目录 | GET `/events` |
| 获取投递渠道 | GET `/channels` |
| 校验配置 | POST `/_validate` |
| 创建订阅 | POST，无后缀 |
| 修改订阅 | PUT `/{subscriptionId}` |
| 启用 / 停用 | POST `/{subscriptionId}/_enable`、`/{subscriptionId}/_disable` |
| 查询订阅 | POST `/_query` |

事件目录按提供方返回 id、name、events。保存使用 events 中的稳定事件 ID，不保存中文显示名；事件范围配置按对应事件源要求填写。创建、修改和校验使用相同结构：

```json
{
  "name": "设备事件通知",
  "description": "将授权范围内的设备事件发送到接收服务",
  "scopes": [
    {
      "eventTypes": ["<从事件目录选择的ID>"],
      "configuration": {}
    }
  ],
  "channelProvider": "http-hook",
  "channelConfiguration": {
    "endpoint": "http://127.0.0.1:19090/webhook",
    "method": "POST",
    "headers": {}
  }
}
```

先替换事件 ID、范围配置和接收地址，再校验、保存并启用。不要把 Client Secret、signingKeyRef 或自定义签名头放入渠道配置；平台按应用归属读取当前有效 OAuth2 凭据。启用时应用凭据必须有效，草稿保存不等于订阅已运行。

## 3. 签名怎么验证

API 订阅使用 **Client ID 作为 X-Key-Id，Client Secret 作为 HMAC Secret**，不使用业务模板通知密钥或用户 Token。

| Header | 含义 |
| --- | --- |
| `X-Signature-Version` | 固定字符串 1 |
| `X-Application-Id` | API 应用记录 ID，不是 Client ID，也不是设备 ID |
| `X-Key-Id` | 当前 Client ID |
| `X-Timestamp` | 本次发送时间，epoch 毫秒 |
| `X-Event-Id` | 正文事件 id，重试不变 |
| `X-Signature` | HMAC-SHA256，Base64URL 无 padding |

**API 订阅不发送 X-Platform-Id，但签名仍包含一个空平台字段。** 因此是六个 HTTP 签名头、七个 MAC 输入字段，不能省略空字段的四字节长度。

```text
LP(s) = 4字节大端UTF-8字节长度 || UTF8(s)
input = LP("1") || LP(applicationId) || LP("") || LP(clientId)
     || LP(timestamp) || LP(eventId) || LP(SHA256(rawBody)的小写hex)
signature = Base64URL无padding(HMAC-SHA256(UTF8(clientSecret), input))
```

使用 Secret 原文，不做 Base64 解码。保留原始 body，不解析后重新序列化；校验签名头唯一性、应用/Client ID、时效（示例 ±5 分钟），以恒定时间比较签名，再核对正文 id。subject 是设备等事件主体，不代表接收应用；API data 中出现 application 字段也不应切换为业务通知协议。

验签是本地计算，不需要回调平台，也不是解密。HMAC 不隐藏 JSON，仍需 HTTPS。密钥重置后，后续发送及重试使用新凭据，接收方同步更新；缺少有效凭据时平台不降级无签名发送。

## 4. 运行 Python 接收示例

[订阅接收脚本](../../tools/python/subscription_receiver.py)使用 Python 标准库，无需安装额外依赖。从项目根目录的交互终端启动：

```sh
python tools/python/subscription_receiver.py
```

按提示输入应用 ID、Client ID、Client Secret；Secret 隐藏输入，不通过命令行参数传入，不落配置文件。

- 默认监听 `127.0.0.1:19090`，接收路径 `/webhook`，健康检查 `/health`。
- 日志默认写入 `data/subscription-receiver.jsonl`。每次记录验签结果、事件 ID、原始 JSON、结构化 body 及 SHA256，终端也会输出业务正文。
- 可通过 `--host`、`--port`、`--log` 修改监听和记录位置。远程部署时接收地址须平台可达，不照抄本机回环地址；不直接向公网暴露调试服务。
- 每个进程只绑定一个 API 应用。Secret 重置后重启此脚本并重新输入新值；这不要求平台重启。
- 未验签正文、Secret、Cookie、Authorization 和 X-Signature 不写日志。已验签业务正文可能敏感，请控制本地文件权限和保留时间。

在平台填好 /webhook 地址并启用订阅，再触发权限范围内的真实事件。成功响应包含 verified=true 和 eventId；401 通常为凭据、签名或时钟错误。

该示例只记录通知，不执行业务副作用，也不阻止重复记录。生产接收端需按应用与 eventId 持久去重，可靠受理后才返回 2xx，异步业务失败由自己的 inbox 恢复。

## 5. 自动重试和按订阅恢复

自动重试间隔：**10 秒 → 30 秒 → 1 分钟 → 5 分钟 → 15 分钟 → 30 分钟 → 1 小时**，末档后继续按 1 小时，最长重试窗口为 **24 小时**。

网络离线、超时以及 408/429/5xx 可有限重试；其他 4xx 属于永久拒绝。终止的失败任务不会因为接收端重新上线而自行恢复，也不保证无限期离线后补齐全部数据。

恢复接收服务后，按订阅重试失败任务：

```http
POST /application/{applicationId}/subscriptions/{subscriptionId}/_retry-failed
Content-Type: application/json

{}
```

请求体可省略，默认选择**最近 12 小时内失败**的任务。可传 startTime/endTime（epoch 毫秒）；endTime 不超过操作开始时刻，startTime 缺省为结束时间前 12 小时。范围按失败时间筛选，返回重新排队数量，不代表对方已收到。

此操作要求父应用/订阅对应的保存权限，不提供无时间边界的全量重置，恢复大量数据时应分时段操作。24 小时自动重试窗口与默认 12 小时人工筛选是不同含义；业务模板通知也不套用该 API 订阅策略。

## 6. 查看推送记录和实际 JSON

以下三个接口的前缀为 `/application/{applicationId}/subscriptions/{subscriptionId}`，都需要相应查询和数据权限。

| 接口 | 用途 |
| --- | --- |
| POST `/tasks/_query` | 查询任务状态和重试进度 |
| POST `/records/_query` | 查询各次投递尝试及响应/错误 |
| GET `/tasks/{taskId}/attempts/{attempt}/payload` | 查询该次实际准备的报文 |

分页请求示例：

```json
{"pageIndex": 0, "pageSize": 20}
```

报文包含 body（结构化 JSON）、rawBody（原始 JSON 字符串）、sha256，以及 taskId/eventId/attempt 等定位字段，保存在时序存储中并遵循其生命周期。任务还在不代表历史报文永久保留。

报文落库在 HTTP 发送之前，因此仅有报文记录只能证明准备发送。对账时结合投递尝试、响应结果和接收端 eventId 记录；网络超时也可能发生在对方已接收之后，重试必须幂等。2xx 不证明对方已完成业务处理。

## 7. 常见问题

| 现象 | 检查 |
| --- | --- |
| 管理员能创建订阅但启用无权限 | 应用接口许可、创建人当前数据身份、目标资产及租户范围 |
| 平台产生事件但没有通知 | 订阅是否启用、事件类型和范围、应用凭据、网络地址及任务状态 |
| 签名正确算法却一直失败 | 是否遗漏空平台字段、混用应用 ID/Client ID、重新序列化正文，或 Secret 已轮换 |
| 接收端恢复但仍没有补发 | 是否已进入终止状态或超出窗口；用带时间范围的订阅重试接口恢复 |
| 有记录但查不到正文 | 报文是否成功留存、时序生命周期是否已过期、查询是否在正确应用/订阅范围 |

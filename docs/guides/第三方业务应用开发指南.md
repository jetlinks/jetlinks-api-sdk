# 第三方业务应用开发指南

接入流程：**配置模板与密钥 → 接收应用凭据 → 用户登录或后台调用 → 处理变更通知**。平台操作见[接入说明](第三方业务应用接入说明.md)。

## 1. 接入准备

| 配置 | 来源与用途 |
| --- | --- |
| 通知 URL | 接收方提供，平台服务端必须可达；生产使用 HTTPS |
| 登录回调 URL | 接收方实现，供浏览器跳转；不要填 Python 接收示例的通知地址 |
| RSA 接收 keyId、公钥 | 接收方生成，公钥交给平台，私钥仅留接收端 |
| 通知签名 keyId、Secret | 管理员在模板页生成，通过安全渠道交给接收方 |
| platformId、templateId | 双方确认的可信来源；platformId 默认模板 ID |
| 应用及成员授权 | 平台配置功能许可、数据范围和可登录用户 |

先保存模板基本信息，再生成通知凭据，最后保存通知地址和 RSA 配置。`notification.keyId` 是 RSA 接收 ID，`X-Key-Id` 是 HMAC 签名 ID，二者不能混用。平台主密钥、模板 secureKey 不交给第三方。

## 2. 接收通知与应用凭据

### 2.1 验签协议

| Header | 内容 |
| --- | --- |
| `X-Signature-Version` | 固定字符串 1 |
| `X-Application-Id` | 应用实例 ID |
| `X-Platform-Id` | 平台来源标识 |
| `X-Key-Id` | 模板通知签名 keyId |
| `X-Timestamp` | 本次发送时间，epoch 毫秒 |
| `X-Event-Id` | 正文事件 id，重试保持不变 |
| `X-Signature` | HMAC-SHA256 的 Base64URL 编码，无 padding |

```text
LP(s) = 4字节大端UTF-8字节长度 || UTF8(s)
input = LP("1") || LP(applicationId) || LP(platformId) || LP(keyId)
     || LP(timestamp) || LP(eventId) || LP(SHA256(rawBody)的小写hex)
signature = Base64URL无padding(HMAC-SHA256(UTF8(secret), input))
```

保留原始 body，不重新序列化 JSON，不对 Secret 做 Base64 解码。拒绝缺失或重复签名头，检查时间窗口（示例 ±5 分钟），以恒定时间比较签名。

验签后核对正文 id、应用 ID 和模板归属；首次通知只能通过预先信任的模板密钥建立应用绑定，已知应用不能改绑其他模板。以 `(platformId, applicationId, eventId)` 持久化去重，再返回 2xx；不要先返回成功再保存消息。

HMAC 不加密正文，也不是不可否认性证明。2xx 表示接收成功，不代表业务处理完成。业务模板默认最多尝试 5 次（含首次），以实际投递策略为准；408/429/5xx 可有限重试，其他 4xx 为永久拒绝。

### 2.2 应用凭据通知

```json
{
  "id": "event-001",
  "type": "application.created",
  "version": "1",
  "occurredAt": 1792108800000,
  "subject": "app-001",
  "data": {
    "application": {
      "id": "app-001",
      "templateId": "partner-template",
      "name": "合作方应用",
      "apiBaseUrl": "https://platform.example.com/gateway",
      "state": "enabled"
    },
    "payload": {
      "credential": {
        "accessKey": "<AccessKey>",
        "encryptedAccessSecret": "<标准Base64密文>",
        "keyId": "receiver-rsa-1",
        "keyRevision": 1
      }
    }
  }
}
```

按 `credential.keyId` 选择私钥，用 **RSA-OAEP-SHA256、MGF1-SHA256** 解密 encryptedAccessSecret。安全保存 `platformId、applicationId、apiBaseUrl、accessKey、accessSecret、keyRevision`。

- 凭据事件包括 created、credential.rotated、credential.synced；完整事件名均以 `application.` 开头。
- 基本信息按 occurredAt 防止迟到覆盖；同一生命周期按 keyRevision 更新凭据，变化时清理旧 Token 缓存。保留删除时间，避免迟到事件恢复已删除应用；重建后 revision 可能从 1 开始。
- API 地址只取已验签通知的 apiBaseUrl，拼接请求路径时保留网关前缀；浏览器参数不能覆盖该地址。
- 仅丢失本地记录时，由管理员“同步接入信息”，不必轮换应用凭据。

模板通知换钥会影响全部所属应用，后续发送和重试使用新 keyId/Secret，在途请求可能仍用旧值。无双密钥宽限期，接收方应同步更新；换通知密钥不改变 RSA 配置或应用 AccessSecret，也不自动补发所有历史事件。

## 3. 用户登录

### 平台发起

已登录且绑定应用的用户调用 `GET /business-application/{applicationId}/_redirect`，读取 JSON 的 result.location 后由浏览器导航。第三方回调收到 platformId、applicationId、code：前两项只用于查找已登记应用，不是身份凭据。

平台入口不自动附带 state/PKCE。真实接入建议将平台到访转为第三方发起的 state/PKCE 授权，绑定当前浏览器和目标应用，不无条件接受任意 Code。

### 第三方发起

通过已登录的平台入口调用 `GET /oauth2/authorize`，携带 response_type=code、client_id、redirect_uri、state；需要 PKCE 时传 code_challenge_method=S256 和 challenge。state 保存在当前浏览器关联的服务端会话，回调时核对并一次消费。

```text
code_challenge = Base64URL无padding(SHA256(ASCII(code_verifier)))
```

授权接口返回 JSON result 中的回调 URL，由调用方导航。回调不得带 fragment，可在模板登记地址的同源范围内选路径和 query；兑换必须使用原始、精确匹配的 redirect_uri。

### 兑换并核验身份

第三方后端使用应用凭据兑换 Code，PKCE 流程同时提交原 code_verifier：

```http
POST {API_BASE}/oauth2/token
Authorization: Basic <Base64(AccessKey:AccessSecret)>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=<Code>&redirect_uri=<URL编码后的回调>&code_verifier=<原始verifier>
```

未使用 PKCE 时不传 code_verifier。也可改用表单 client_id/client_secret，不能与 Basic 同时使用。成功响应直接返回 access_token、token_type、expires_in、scope，不包 result。Code 默认 5 分钟有效、一次消费；超时结果不明时重新授权，不反复使用旧 Code。

用用户 Token 调用 `GET /authorize/context`，核对 application.id 与当前应用一致、主体为真实用户，以 `(platformId, applicationId, subject.id)` 建立本地用户映射。需要 username 时用同一 Token 调 `GET /user/detail` 并核对用户 ID；回调里的提示值不能直接建立会话。

Token 留在后端，浏览器使用受保护的第三方会话。无 Refresh Token 或 OIDC ID Token，用户 Token 过期须重新授权。第三方自行处理会话期限、退出、解绑和权限刷新。

## 4. 后台调用与授权同步

后台任务用应用凭据申请应用 Token：

```http
POST {API_BASE}/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=<AccessKey>&client_secret=<AccessSecret>
```

按 expires_in 缓存复用，默认有效期 15 分钟。业务应用后台使用实例自身授权，不继承创建人权限；用户委托取用户与应用功能许可的交集。Scope 只收窄功能范围，不移除数据限制：不传使用默认许可，传空格分隔 Group ID 选择范围，显式空值表示零功能许可。

所有业务请求携带 `Authorization: Bearer <Token>`。收到变更提示后可查询：

| 查询 | 接口 | 功能权限 |
| --- | --- | --- |
| 成员 | `POST /user/detail/business_application/{id}/_query` | user:query |
| 角色 | `POST /role/_query`，按 applicationId 过滤 | role:query |
| 用户角色关系 | `POST /business-application/{id}/user-roles/_query` | business-application:query、user:query、role:query |
| API Group | `POST /business-application/{id}/api-grants/_query` | business-application:query、api_group:grant_query |
| 角色授权 | `POST /business-application/{id}/roles/{roleId}/authorization/_query` | business-application:query、role:query |
| 角色菜单 | `POST /business-application/{id}/roles/{roleId}/menus/_query` | business-application:query、role:query、menu:query |

分页从 pageIndex=0 开始，读取 result.total/data。结果仍受数据权限约束；403、空结果或同步失败不能直接触发全量删除本地用户。通知是刷新提示，不是权限全量快照。

## 5. 可选：提供命令接口

需要平台主动调用第三方时，在模板配置 `api.address`，接收方提供能力发现与命令端点：

| 接口 | 内容 |
| --- | --- |
| GET /api/capabilities | 返回支持的版本及命令 ID，例如 v1 的 GetMetrics、ReadUsage |
| POST /api/commands/1/{commandId} | JSON 参数；单结果 application/json，多结果 application/x-ndjson |

命令使用实例 AccessKey/AccessSecret，不用通知密钥。请求和响应均携带版本、应用、平台、keyId、时间、requestId 和签名；LP/HMAC 编码字段如下：

```text
request  = ["http-command", "1", "request", applicationId, platformId, keyId, timestamp, requestId,
            method, target, contentType, accept]
response = ["http-command", "1", "response", applicationId, platformId, keyId, timestamp, requestId,
            requestSignature, status, contentType]
```

method 大写，target 为原始 path/query；缺失 Content-Type/Accept 编码空字符串。错误响应也签名。此签名绑定身份及请求关联，正文完整性依赖 HTTPS；有副作用的命令另做业务幂等。下面的 Python 接收脚本不实现命令服务。

## 6. 本地联调

[业务应用接收脚本](../../tools/python/business_application_receiver.py)只示范通知验签、RSA 解密和持久去重，不提供页面、登录回调或完整用户系统。以下命令从项目根目录执行，使用 Python 3.11+。

### 安装并准备配置

```sh
python -m pip install -r tools/python/requirements.txt
```

先创建本地 data 目录，准备至少 2048 bit RSA 私钥及对应 SPKI 公钥。已有密钥可直接使用；安装 OpenSSL 的环境可生成：

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out data/receiver-private.pem
openssl pkey -in data/receiver-private.pem -pubout -out data/receiver-public.pem
```

不要覆盖正在使用的密钥。公钥交平台，私钥只留接收端。创建受保护的 `data/business-receiver.json`，填入模板页面取得的真实通知凭据：

```json
{
  "key_id": "receiver-rsa-1",
  "private_key_file": "receiver-private.pem",
  "templates": [
    {
      "platformId": "partner-prod",
      "templateId": "partner-template",
      "keyId": "<模板通知签名keyId>",
      "secret": "<模板通知Secret原文>"
    }
  ]
}
```

私钥路径相对 JSON；templates 可配置多个受信模板，每个平台/模板只保留当前一组通知凭据。配置文件含 Secret，限制文件权限，不提交仓库或写入日志。

### 启动与验证

```sh
python tools/python/business_application_receiver.py --config data/business-receiver.json
```

默认仅监听 127.0.0.1:18080，通知路径 `/jetlinks/events`，健康检查 `/health`。远程联调可通过 --host/--port 修改监听，模板 URL 必须从平台服务端可达；生产使用 HTTPS 入口，不直接暴露调试服务。

在平台保存通知配置后创建应用，或对已有应用“同步接入信息”。正常响应为：

```json
{"accepted": true, "duplicate": false, "credentialReceived": true}
```

- 验签、归属校验及 RSA 解密通过后，将原始通知写入 `data/business-notifications.sqlite3`；重复事件返回 duplicate=true。
- 库中保留原始报文和应用模板绑定，应用 Secret 仍为通知中的 RSA 密文。解密结果只在内存中的 Credential 对象，不返回或输出明文 Secret。
- 实际接入可复用 Receiver.verify/decrypt，在自己的安全存储中保存应用凭据并处理 revision。示例的接收成功不代表已建立业务账户、调用 API 或处理全部生命周期。
- 通过 --database 指定独立 inbox。保留数据库可在重启后继续去重；报文可能含敏感业务数据，应自行管理文件权限及保留时间。
- 平台换通知密钥后更新 templates，文件替换完成后后续验签读取新值，无需重启；在途请求可能仍用旧值。RSA 接收 ID 和私钥仅启动时读取，更换它们需要重启并安排密文处理。
- 脚本接收上限 128 KiB，仅用于轻量通知联调；生产按实际报文规模设计接收能力。

## 7. 常见问题

| 现象 | 处理 |
| --- | --- |
| 保存平台通知配置失败 | 先保存模板、生成并保存通知凭据，再保存通知配置 |
| 通知未知 keyId / 验签失败 | 核对 templates 中的平台、模板及 keyId/Secret，原始 body、签名头和时钟 |
| 验签通过但解密失败 | 核对 RSA 接收 keyId、私钥、公钥及 OAEP/MGF1 SHA-256 |
| 接收成功但不能在脚本页面登录 | 脚本没有页面或登录接口；用户登录按第 3 节自行实现 |
| Token 有效但 403 / 空数据 | 检查功能许可、实例资产授权、用户范围及 Scope，不用后台身份替代用户 |
